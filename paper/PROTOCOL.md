# Analysis protocol for paper 1

**Frozen on 21 November 2026.** This protocol is binding from the commit that carries this line, made before the first campaign run. Pilot and trial runs made before it are reported as such and are not part of any arm. Anything changed afterwards is listed in section 9 with its date and reason.

## 1. Question

Does independent re-evolution reproduce the scores and body types of Cheney et al. 2013, and what moves the outcome when it does not?

## 2. Arms

Population 30 in every arm, as in 2013. Seeds are the unit of analysis.

| Arm | Simulator | Search | Condition | Seeds | Generations |
|---|---|---|---|---|---|
| R | Original 2013 simulator | **Original 2013 search program**, both built from the authors' source (`run_2013_search.sh`) | No cost | 1–35 | 1000 |
| Rc | Original 2013 simulator | Original 2013 search program | Actuated cost (its `-P 2`) | 1–35 | 1000 |
| A | Original 2013 simulator (`--simulator voxelyze2013`) | This project's CPPN-NEAT as it is (`--no-age-pareto`) | No cost | 1–35 | 1000 |
| D | MuJoCo engine with `--preset cheney2013` | This project's CPPN-NEAT as it is | No cost | 1–10 | 300 |
| E1 | MuJoCo engine, preset, global damping back to 0.01 | Same | No cost | 1–3 | 300 |
| E2 | MuJoCo engine, preset, amplitude ±20% with the volumetric law on | Same | No cost | 1–3 | 300 |
| E3 | MuJoCo engine, preset, the soft floor of September 2026 | Same | No cost | 1–3 | 300 |

The arms form a ladder. R and Rc re-execute the original code with new seeds: does the experiment repeat? A replaces the search with an independent one in the same simulator. D replaces the simulator as well. E1 to E3 each undo one physics setting.

*Amended on 25 November 2026, before arms D and E had started (section 9.5): for arms D, E1 and E2 "preset" in the table now means `--preset cheney2013-floor`, the preset with the 2013 simulator's own floor and start. Arm E3 is no longer the soft floor of September 2026 but the hard floor: the engine with `--preset cheney2013` as it was, seeds 1 to 3, 300 generations.*

Arms R and Rc are started with `paper/reference_2013/start_arm.py`. Their runs are named `armR_P0_s<seed>` and `armRc_P2_s<seed>`.

## 3. Reference data

The deposited 2013 data: champion score by generation for 35 runs per condition (`softbots2013GenchampData.tgz`), and the generation-1000 robots (`softbots2013Gen1000.tgz`). The no-cost condition is the reference for arms R, A, D and E; the actuated-cost condition for arm Rc.

## 4. Outcomes

A run's champion at a generation is the individual with the best fitness (after any penalty) in that generation; its score is its original, unpenalised 2013 score. The best such score up to that generation is used, and the deposited curves are read the same way.

- **Primary.** Champion score at generation 1000 for arms R, Rc and A; at generation 300 for arm D. Each is compared with the deposited runs at the same generation, and A also with R.
- **Secondary, scores.** The same at generations 100 and 300.
- **Secondary, body.** For each run's final champion: voxels, footprint, fill of the bounding box, muscle fraction, and whether it has two or more separate feet, all from `morphology_scorecard.body_metrics`, the same code used on the deposited robots.
- **Secondary, transfer.** Every champion of arms R, Rc and A scored in the MuJoCo engine with the preset; every champion of arm D scored in the 2013 simulator.

## 5. Statistics

- Two-sided Mann-Whitney U, each arm against the deposited runs. Holm correction over the five primary comparisons (R, Rc, A and D against the deposit, A against R), and separately within the body measures.
- Effect size: Vargha-Delaney A12 with a bootstrapped 95% interval.
- Bootstrapped 95% interval of the ratio of medians (arm over deposited), 10,000 resamples of runs.
- **Reproduction criterion, fixed in advance:** an arm reproduces its reference condition if that interval of the ratio of medians lies inside 0.90 to 1.10. Otherwise the gap is reported with its interval. The floor measured for the original code itself (same source, different compiler) is reported alongside.

## 6. Rules

- Every seed is reported, including failures.
- A run that dies is never replaced by another seed. A run of this project's search is resumed from its checkpoint. A run of the original program (arms R and Rc) is started again from the beginning with the same seed: that program gives the same run for the same seed (section 8, point 2), so this repeats the lost run. Its own restart switch (`-X`) is not used, because it has not been validated here. The unfinished attempt is kept, and the paper reports how many seeds were started more than once.
- No arm is extended, shortened or re-seeded after its results have been looked at.
- If a defect is found in the code, the whole affected arm is rerun and the paper says so.
- Every champion gets the audit (reproduced score, and for MuJoCo champions a quarter time step and floor penetration). The audit is reported; it is not used to drop runs.
- Each run's `manifest.json` records its command, settings and code version. Arms R and Rc are not started by this project's evolution script, so their launcher records the same in `results/rerun2013/<arm>_launches.json`, together with the checksums of the two programs, their libraries and the settings file, and refuses to continue an arm on a different build.
- The campaign runs from the code tagged `campaign-v1`. Later commits may add documentation and analysis; they do not change what a run computes. *(Amended on 23 November 2026 for arms A, D and E, which run from `campaign-v2`: section 9.3. Amended for arms D and E on 25 November, `campaign-v3`, section 9.5, and on 27 November, `campaign-v4`, section 9.6.)*

## 7. Exploratory, and labelled as such in the paper

Everything not listed above: porting single 2013 search settings into this project's CPPN-NEAT to find which one matters, this project's search under the cost condition, conditions that favour limbs, gravity, longer runs, other search methods.

## 8. Points settled at the freeze

The draft of this protocol left three points open and one rule imprecise. They were settled as follows when it was frozen.

1. **Seeds for arm D and for E1 to E3** are as in the table: 10 and 3. The cost of a MuJoCo run under the preset has not been measured yet; a timing pilot will measure it. If it shows that an arm cannot finish in time, the arm's seeds or generations may be reduced only before its first run is started, and the change is recorded in section 9.
2. **How many runs share the machine.** All 35 runs of arm R, and later of arm Rc, run side by side, one core each. This is a matter of machine time, not of design: for a given seed the original program gives the same scores however many runs share the machine, and when it is started again. Checked before the freeze: seeds 1 to 3 over ten generations, three side by side against twelve side by side, every score identical; seeds 1 and 2 cut short and started again, identical over the two generations run. The two programs were also rebuilt from the scripts in this repository and came out byte for byte the ones the pilot ran with.
3. **This project's search under the cost condition** stays exploratory (section 7). It is not an arm.
4. **Runs that die.** The draft said such a run "is resumed from its checkpoint". For the original program that is replaced by starting the same seed again from the beginning (section 6), which point 2 shows to be the same run. No seed is ever replaced by another.

## 9. Changes after the freeze

No change to the outcomes, the tests or the criterion, and none to arms R, Rc and A. The engine settings of arms D and E were changed once, before either had started (section 9.5). Their code was changed once more, also before either had started, without changing what an evaluation computes (section 9.6).

### 9.1 Details of the analysis, fixed on 22 November 2026

Fixed on the evening of 22 November 2026. Arm R had finished at 21:40 and its launcher had printed its closing summary in the campaign window; these details were written without consulting that summary or any other result of the arm. Up to then the analysis had read only the runs' generation counts and file counts. The analysis is `paper/analysis/analyse_arm.py`. It was developed and tested on the pilot runs and on arms made up from the deposited runs themselves, and committed before it was first run on an arm.

1. **Scores.** A run's score at generation g is the largest champion original fitness (column 2 of the program's learning-curve file) in generations 1 to g. The deposited curves are read the same way.
2. **Final champion.** The robot with the highest adjusted fitness in the population of the last generation, by the fitness in its file name. Ties go to the first file name. The same rule picks the champion of each deposited run.
3. **Body measures.** From `morphology_scorecard.body_metrics`: voxels, footprint, fill, muscle fraction (the two muscle materials over all voxels), and "two or more separate feet" as its `feet` count being 2 or more, where feet are the separate face-connected patches of the body's lowest layer.
4. **Bootstrap.** 10,000 resamples. The arm's runs and the reference runs are each resampled with replacement, independently. The interval runs from the 2.5th to the 97.5th percentile. The random seed is fixed at 0 and the runs are taken in seed order, so a report can be reproduced to the last digit.
5. **Tests.** Mann-Whitney U, two-sided, as SciPy computes it by default. The one yes/no measure, two or more feet, is tested with Fisher's exact test, two-sided.
6. **Holm.** The five primary comparisons are one family. Its correction can be computed only when all five exist; until then a report gives the uncorrected p and the range the corrected one can still take. The body measures are corrected within each arm: its five measures against the deposit are one family.
7. **Reading the criterion.** Three outcomes, by the 95% interval of the ratio of medians. Inside 0.90 to 1.10: the arm *reproduces* its reference. Not inside, but containing 1: the arm is *not distinguishable* from its reference, and reproduction within 10% is not shown. Excluding 1: the arm *differs*.
8. **Whole arms only.** The analysis computes nothing for an arm while one of its seeds is unfinished. A seed that fails again when it is started again is reported and left out of the statistics, which then say how many runs they use.

### 9.2 What the criterion can show, computed on 22 November 2026 from the deposited runs alone

How often would a perfect reproduction meet the criterion? New runs were drawn from the deposited runs themselves, so that they come from the same distribution by construction, and analysed like an arm (`analyse_arm.py --what-can-the-criterion-show`).

| Design | A perfect reproduction meets the criterion in | The deposit against itself gives the interval |
|---|---|---|
| Arms R and A: 35 runs, generation 1000, no cost | 66% of cases | 0.94 to 1.06 |
| Arm Rc: 35 runs, generation 1000, actuated cost | 0% of cases | 0.85 to 1.17 |
| Arm D: 10 runs, generation 300, no cost | 17% of cases | 0.93 to 1.08 |

The criterion is unchanged, and these figures are reported with each result. In the cost condition the median of 35 runs is too unsteady for a 10% window, so arm Rc can only come out as "not distinguishable" or "differs". With 10 runs the same holds for arm D in five cases out of six.

### 9.3 The code of arms A, D and E: one correction, 23 November 2026

Made with the author's approval of that day, before any run of these arms was started.

- **What was found.** A trial of arm A's launcher showed that a run of this project's search which is stopped and continued from its checkpoint did not compute what it would have computed without the stop. While a run is alive, the search loop and the genomes share one random generator; the checkpoint brought them back with separate copies of it. With tournament selection, the scheme of arms A, D and E, this went wrong only when a run was stopped before its second generation was recorded. With age-fitness selection it went wrong at any generation.
- **What was changed.** The checkpoint now holds the generator itself next to the genomes, and a continued run uses it: two statements in `run_tendon_evolution.py`. Nothing else.
- **What it does not change.** An uninterrupted run computes what it computed before. Arms R and Rc do not use this code.
- **Evidence.** `tests/test_resume_exact.py` fails on the code tagged `campaign-v1` and passes on the corrected code, for both selection schemes. In the 2013 simulator, seeds 1 and 2 stopped during their second generation and continued are identical to their uninterrupted runs with the corrected code (`dryT`); with the old code they differed (`dryS`). Uninterrupted, seed 1 gives the fitness of all 30 robots of the pilot of 21 November in each of the four generations compared, with the corrected code (`dryU`) as with the old one (`dryQ`).
- **Consequence for section 6.** Arms R and Rc ran from the code tagged `campaign-v1`. Arms A, D and E run from the code tagged `campaign-v2`, which differs from it in what a run computes only by this correction. A run of these arms that is continued from its checkpoint is then the same run as an uninterrupted one. The paper reports which runs were continued.
- **Known and left alone.** `history.json` of a continued run lists the generation it was continued from twice; the analysis reads the numbered generation files instead. The MAP-Elites loop, which no arm uses, has the same flaw and was not changed.

### 9.4 The transfer outcome: how it is computed, fixed on 24 November 2026

Section 4 names the outcome and says no more. These details were fixed before any champion of an arm was scored in the MuJoCo engine. The code is `paper/analysis/transfer_scores.py`, committed before it was first run on an arm.

What was known when this was written. On 18 November, before the protocol, the deposited champions had been scored in the MuJoCo engine as a diagnostic, under the settings that became the preset: the no-cost champions kept a median of 0.68 of their recorded scores, the cost champions 0.77 (`paper/diagnostics_2026-11-18/`). On 24 November one robot of the 12-seed pilot (seed 1, generation 10) was scored to measure how long an evaluation takes: 1.78 against 1.37 in the 2013 simulator. Nothing of arms R, Rc or A.

1. **Which robots.** The final champion of every run, as picked in 9.1 point 2: of arms R, Rc and A, and of the 35 deposited runs of each condition, which are scored the same way and serve as the comparison. An arm's champions are scored only after the arm's own analysis.
2. **The engine.** The evaluation of this project's search with the values of `--preset cheney2013`, which are the settings of arm D: beam bodies with the 2013 materials, the hard floor with friction 1.0 static and 0.5 kinetic, 40 Hz, amplitude ±14%, no volumetric coupling, global damping 0.001, 0.25 s measured from the start, score = distance moved by the centre of mass in any direction over the width of the 10-voxel workspace. The values are read from the preset in `run_tendon_evolution.py`, not typed again.
3. **One evaluation per champion, over the whole 0.25 s.** The search stops a robot early when it has moved less than 0.05 of the workspace width after a fifth of the time, and scores it on that part. For this outcome the early stop is switched off. A body whose simulation blows up scores 0, as in the search; it is counted and stays in the statistics.
4. **The transfer ratio** of a champion is its score in the other simulator over its score in the simulator it was evolved in: how much of its score it keeps. For a champion of arms R, Rc or A the score it was evolved with is its recorded original score. A deposited champion was evolved with the 2013 build of the simulator, which is not the build of this campaign (reference README, section 1); its ratio is taken against its score in this campaign's build, from the replay of all deposited robots (`replay_2013_simulator.csv`), so that both numbers of every ratio come from the programs of this campaign. The score recorded in 2013 is reported next to it.
5. **Statistics, all descriptive.** For each set of champions: how many, and how many blew up; median and quartiles of the score in the other simulator; median and quartiles of the transfer ratio, with a bootstrapped 95% interval of that median (10,000 resamples of the champions, random seed 0, champions in seed order, deposited runs in the order of the body analysis); Spearman's rank correlation between the two simulators' scores, with the same bootstrap. Each arm against the deposited champions of its condition, and arm A also against arm R, on the transfer ratio: A12 with its bootstrapped interval and the two-sided Mann-Whitney test, as in section 5. No criterion is attached. These p-values are not part of the Holm family of the primary comparisons and are reported uncorrected.
6. **Recorded with every evaluation, not used in the statistics:** how far the centre of mass moved along each axis, the time step the engine chose, how deep the lowest voxel sank below the floor's surface, and the lowest layer of the workspace the body occupies (the MuJoCo engine sets every body on the floor before it starts).
7. **A check of the numbers, not an outcome.** The champions of seeds 1 to 5 of each arm, and of the first five deposited runs of each condition, are scored once more with a quarter of the time step, the check section 6 asks for MuJoCo champions. The seeds are named here so that the choice cannot follow the results. The differences are reported; nothing is dropped or corrected because of them.
8. **Arm D** is treated the same way in the other direction: its champions are scored in the 2013 simulator, and their ratio is that score over the score they were evolved with.
9. **Added later the same day, still before any champion of an arm was scored in the MuJoCo engine.** Reading the champions' bodies for point 6 showed that 16 of arm Rc's 35 champions and 12 of the 35 deposited cost champions do not touch the bottom of the workspace: their lowest voxels are 1 to 3 layers up. So does 1 champion of arm R, and none of the deposited no-cost champions. The two simulators start such a body differently. The 2013 simulator starts it where it is, in the air, and its score, a distance in three dimensions, includes the drop (checked in the recording copy of the simulator on the deposited cost champion of run_114: it starts 3 voxels up, falls for about 15 ms, and the distance the simulator reports is the three-dimensional one). The MuJoCo engine sets every body on the floor before it starts. Every champion that does not touch the bottom is therefore scored a second time in the MuJoCo engine, started at its height in the workspace (the engine's own `initial_height`; no change to its code), and the statistics of point 5 are given both ways. Set on the floor is the preset as it is and stays the outcome named in section 4; started where it is in the workspace is reported next to it. Whether arm D should start its bodies the way the 2013 simulator does is a question about arm D's settings, not about this outcome; it is open and has to be settled before arm D starts. *(Settled on 25 November 2026: section 9.5.)*

### 9.5 Arms D and E: the floor and the start of the 2013 simulator, 25 November 2026

Made with the author's approval of that day, before any run of arms D or E was started. Arm A was running; it uses the 2013 simulator and is not touched by this.

- **What was found.** The transfer outcome of section 9.4, scored on 24 November for arms R and Rc: champions evolved in the 2013 simulator keep a median of 0.43 to 0.85 of their score in the MuJoCo engine under `--preset cheney2013`. Two things in which that preset is not the 2013 simulator were found with it. Where a body starts (section 9.4, point 9). And the floor: the 2013 simulator's floor, read from its source (`CVXS_Voxel::CalcFloorEffect`), is a spring on the centre of each contact voxel, `E × size/2 × (size/2 − z)`, with a friction rule that brakes a sliding voxel and, once the brake would stop it within one time step, stops it dead and holds it. Under a champion's weight it gives 0.14 to 0.29 of a voxel at rest. The engine's floor under the preset is hard. An exploratory test on 25 November (`paper/diagnostics_2026-11-25/`, with what would count for and against it committed before any champion was scored) emulated the 2013 rule on the engine: the same champions then keep a median of 1.02 to 1.16 of their score, and softer contacts of MuJoCo's own kind do not have that effect.
- **What was changed.** Two options were added to the engine and the search, and one preset. `--floor-contact rule2013`: the floor rule of the 2013 simulator in place of MuJoCo's contact. `--start workspace`: a body starts where it is in the workspace. `--preset cheney2013-floor`: `cheney2013` with both. Nothing else: every default and the preset `cheney2013` are as they were, and a run that does not use the new options computes what it computed before.
- **Arm D** runs with `--preset cheney2013-floor` in place of `--preset cheney2013`. Arms E1 and E2 undo their one setting from that same preset.
- **Arm E3 is the hard floor** (the author's decision of 25 November 2026): `--preset cheney2013` as it was, that is the engine's hard floor with bodies set on the floor, seeds 1 to 3, 300 generations. It takes the place of "the soft floor of September 2026", which leaves the campaign. That floor is MuJoCo's default contact; in the floor test bodies sank 3 to 4 voxels into it and the champions kept a median of 0.35 to 0.57 of their score on it. It had never been defined by flags, and no run of it exists.
- **The transfer outcome** of arms R, Rc and A is reported under both presets. Under `cheney2013` as fixed in section 9.4; that is what was computed for arms R and Rc on 24 November, before anything was known about the floor. Under `cheney2013-floor`, the setting of arm D; for arms R and Rc those scores come from the exploratory test that prompted this change and are reported as such. Arm D's champions are scored in the 2013 simulator as before.
- **What it does not change.** Arms R, Rc and A, the outcomes, the tests and the criterion.
- **Code.** Arms D and E run from the code tagged `campaign-v3`, which differs from `campaign-v2` in what a run computes only by these options. The change was built on a branch of its own (`engine/floor2013`), because arm A's launcher refuses to continue a run when the engine code in the campaign's folder differs from `campaign-v2`. The tag is set when that branch has joined the campaign's branch, after arm A is complete. *(Done on 25 November 2026. Arm A's 35 runs were complete at 23:36. The branch then joined the campaign's branch unchanged, the project's 284 tests passed in the campaign's folder, and `campaign-v3` was set on commit 173a510 at 23:53.)* *(Amended on 27 November 2026: arms D and E run from the code tagged `campaign-v4`, section 9.6.)*
- **Evidence.** `tests/test_floor2013.py`: the rule in the engine gives the same score to the last digit as the emulation that was checked against the 2013 simulator, on the floor and from a height; a block rests where the 2013 simulator rests it; the brake, the stop and the hold act as the 2013 code says; a run of the search under the new preset is repeated score for score by the scoring script; the preset `cheney2013` is unchanged entry for entry. The suites that existed before pass on the new code. And on the champions themselves (`paper/diagnostics_2026-11-25/check_built_in_floor.py`): all 140 champions of arms R and Rc and of the deposit, scored through the search's own evaluation under `--preset cheney2013-floor`, get the scores the emulation gave them in the floor test, 140 of 140 to the last digit; twelve of them scored under `--preset cheney2013` get the scores of the transfer outcome of 24 November, 12 of 12 to the last digit. So the figures of the floor test are the figures of the new preset, and the old preset computes what it computed.
- **The time step stays as it is** (the author's decision of 25 November 2026, on the measurement that follows): arms D and E run with the engine's `DtFrac` of 0.7, like everything scored so far. The 2013 robot files say `DtFrac` 0.9, the engine uses 0.7, and the floor rule depends on the time step, since it stops a voxel when the brake would stop it within one step. Measured on 25 November (`paper/diagnostics_2026-11-25/check_time_step.py`). On the 12 pilot robots, which belong to no arm: at 0.9 they are off from their 2013 scores by 14% in the median, at 0.7 by 18%, at 0.35 by 24%. On the 140 champions that trend is not there: at 0.9, 75 are closer to their 2013 score than at 0.7 and 65 are further, the typical error is smaller in two of the four sets and larger in two, and the rank agreement moves by 0.03 to 0.07 either way. Nothing blew up at 0.9 in either group. With 0.7 kept, arm E3 differs from arm D in the floor and the start only. That the engine's step is 0.78 of the 2013 simulator's, and that the floor rule depends on the step, is reported as a known difference.

### 9.6 Arms D and E: memory, and an evaluation that fails, 27 November 2026

Made with the author's approval of that day, before any run of arms D or E was started. No arm was running.

- **What was found.** On 25 November fourteen processes of the scoring script, next to the runs of arm A, used up the memory Windows could promise to programs, and 86 evaluations failed (`paper/diagnostics_2026-11-25/`, "A lesson about memory"). Two things came out of looking into it. First, a process that evaluates a champion-sized body asked the system for 2.6 to 3.2 GB and used almost none of it: 1.5 GB was set aside by the linear-algebra libraries of numpy and scipy, for one thread on each of the machine's 32 logical processors, and up to 1.7 GB by MuJoCo for a body's contacts, of which an evaluation used about 1 MB. Second, the search's evaluation in the MuJoCo engine gave a body a score of 0 whenever building or simulating it ended in an error, whatever the error, and went on. A run in which memory ran short would have gone on with false scores: no longer the run its seed defines, and with nothing to show it afterwards. No arm had run a search in the MuJoCo engine. Arm A's search runs in the 2013 simulator through another evaluation, and none of its 1,050,000 recorded scores is the value that evaluation gives a lost simulation (checked on 25 November, before the arm's analysis).
- **What was changed.** Three things. None is a setting of an arm.
  1. *One linear-algebra thread per process.* The launcher starts every run with `OPENBLAS_NUM_THREADS`, `OMP_NUM_THREADS` and `MKL_NUM_THREADS` set to 1, and the scoring script sets the same for itself; the processes they start inherit it. A run's `manifest.json` now records these settings as the run was started with.
  2. *An evaluation that fails is not scored.* After an error a body is given 0 only if the error is the body's own: the engine refuses the body or its arithmetic fails (Python's `ValueError` and `ArithmeticError`), and the message does not speak of memory. The run's output says so each time. Any other error (no memory, MuJoCo's fatal error, an error of the operating system, a fault in the code that shows as an error of another kind) stops the run. Nothing of the unfinished generation is recorded, and the run is continued from its last recorded generation, which by section 9.3 makes it the run it would have been. A simulation that blows up is not an error; it scores 0, as before. The rule goes by the kind of error: a fault in the code or in the settings that raises an error of those two kinds is not told apart from a body's own, and such a body scores 0, as it did before, with its line in the run's output.
  3. *MuJoCo's working memory is stated:* 8 MB plus 16 kB per voxel, in place of MuJoCo's own estimate. A body can use 2.9 kB per voxel at most, which is every voxel in contact with the floor at once. Should the stated memory run out all the same, MuJoCo would drop contacts and go on; the engine checks for that in every step and raises an error, which by point 2 stops the run.
- **What it does not change.** What an evaluation computes, and with it every score on record (evidence below). The settings of arms D and E, the outcomes, the tests and the criterion. Arms R, Rc and A.
- **Code.** Arms D and E run from the code tagged `campaign-v4`. It differs from `campaign-v3` in what a run computes in one case only: where an evaluation ends in an error that is not the body's own, the run now stops.
- **Evidence** (`paper/diagnostics_2026-11-27/`, `tests/test_memory.py`). On single evaluations: every evaluation behind the two transfer reports of section 9.5 was computed again with the new code, one thread and the stated memory. That is the 175 champions of arms R, Rc and A and of the deposit under each preset, those that do not touch the bottom once more from their height, and the time-step check: 431 evaluations, which had been computed with the code tagged `campaign-v2` and `campaign-v3`, the libraries' default threads and MuJoCo's own estimate of its memory. All 431 gave the recorded score to the last digit, and none used more than 6.4% of the memory stated for its body. On whole runs: the search's own command line with population 30 and seed 101, which is the seed of no arm, run with the code tagged `campaign-v3` as that code would have run it and with the new code as the launcher starts a run. Five generations under `--preset cheney2013-floor` and three under `--preset cheney2013` are the same runs, score for score (150 of 150 and 90 of 90) and body for body in the final populations. With the new code the scores are the same with one evaluation at a time as with three (60 of 60), and a run that was stopped twice from outside while it ran, and started again each time, is the uninterrupted run (150 of 150). In the tests: a run in which the engine fails once stops, records nothing of the unfinished generation, and continued gives the uninterrupted run, also when it fails in its very first population; with every voxel of a full workspace of 1000 voxels on the floor a body uses 2.8 MB of the 23.6 MB stated; and with too little memory stated MuJoCo either drops contacts, or fails while it builds the model, or fails in the first step, and each of the three stops the search. A process of a run now asks the system for 0.12 GB with the largest champion loaded, against 2.57 GB. The project's 318 tests pass on the new code.
- **Consequence for section 6.** A run of arms D or E that an error stops is continued from its checkpoint. Every start of a run is in the launcher's log and in the run's output, with the error that ended the start before it; a start that got as far as its first population is also in the run's manifest. The paper reports which runs were stopped, how often and by what. A run that stops with the same error each time it is continued has failed in the sense of section 6: it is reported, and no seed is replaced.
- **Known and left alone.** A worker process that dies outright, without raising an error, leaves its run waiting: the run does not go on with a false score, but it does not go on at all until it is stopped and continued. The launcher does that for a run that has recorded no generation for two hours. The body types that no arm uses (`--body springs`, `--flex`) get point 2 and not point 3.
